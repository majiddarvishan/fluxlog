# Fluxlog — bounded hardening implementation plan

**Created:** 2026-10-18  
**Initial baseline:** `main@93e0945e14a34a72ab93d8d048cd1131c523c6b6` (post-upgrade baseline: `main@3323e1316764477b2bb1644aa397cef2fe00d575`)  
**Authorized action for this iteration:** upgrade optional goconfig dependency to **v1.6.0** and plan all other work. **No other runtime source changes**.

## Goals and constraints

1. Keep the core logger isolated from goconfig, with the current public API and serialized write/close model unchanged.
2. Preserve all externally visible format, caller attribution and severity behavior unless a failing test proves a defect and a change is explicitly accepted.
3. Keep dependency/module sums generated by Go tooling; never substitute guessed `go.sum` hashes.
4. Separate discovery, verification and code fixes. A hypothesis is not automatically a bug.
5. Keep each stage small and reviewable; avoid a general refactor or major feature expansion.

**Input:** `adapters/goconfig/go.mod` currently requires goconfig `v1.3.0`; upstream `v1.6.0` is an existing Git tag with compatible exported `Manager`, `Node`, `NewManager`, `NewStrSource` and `OnReplace` entry points. The upstream module's `go.mod` still declares Go 1.18; fluxlog adapter declares Go 1.23.

**Actions:**
1. Bump direct goconfig dependency to `v1.6.0`.
2. Run `go mod tidy` **from `adapters/goconfig`**, update/check `go.sum` and minimal indirect dependency graph. Newer goconfig moves HTTP machinery to a separate `httpserver` package; inspect whether indirect packages are now removable.
3. Verify adapter test suite with `-race`, vet and example build; verify root Go module CI independently.
4. Record reproducible evidence, commit and merge only once CI passes. Neither core code nor `adapter.go` needs an anticipatory rewrite just to bump a dependency.

**Gate:** Dependency-and-plan commit `27cfb35b20158e5fa59050f309c41aeccd7307b0` passed both CI jobs in [run 39144064913](https://github.com/majiddarvishan/fluxlog/actions/runs/39144064913); tidy causes no diff. A final documentation-status commit still requires successful PR CI and merging to main.

## Phase 1 — behavior characterization (later, tests first)

**Order:** `CFG-01` -> `CFG-03` and `CFG-02`, plus `LVL-01` and `FMT-01` independently. Source findings and reproducible scenarios: [REVIEW_2026-10-18.md](REVIEW_2026-10-18.md).

- **CFG-01:** End-to-end `Manager.Replace` with actual `OnReplace` callbacks, including rejection and transactional rollback. Watch for runtime/logger state divergence if persistence fails *after* callback success.
- **CFG-02:** Demonstrate whether two bindings on the same path get callbacks; source inspection shows first-match dispatch in goconfig v1.6.0. Check what the manager retains after `Logger.Close`. If the supported API is one logger per node, document the limitation instead of introducing unnecessary fan-out.
- **CFG-03:** Reproduce a file-persistence error after a successful level-change handler. goconfig v1.6.0 reverts the config node but does not compensate external Logger state. Decide and test the desired rollback guarantee before implementing.
- **LVL-01:** Explicitly define independence: other fluxlog instances vs changes made via zerolog's **process-global** level. State supported semantics before changing filtering.
- **FMT-01:** Reproduce what numeric `zerolog.TimeFieldFormat` values do to console timestamps. Clarify whether Fluxlog is expected to support those configurations.

**Gate:** tests and expected contracts written; fixes only for proven, prioritized and approved issues. The 2026-10-18 Phase 1 **source review** does not satisfy this gate by itself.

## Phase 2 — lifecycle/output hardening (later)

**Order:** `LIFE-01`, `FILE-01`, `ERR-01`, `FMT-02`, with each task capable of its own PR.

- Use race tests for writes during Close, default swap and closed sink outcomes.
- Use deterministic temp-file rotation tests instead of timing-sensitive integration environments.
- Verify actual behavior of failure propagation through zerolog's event writer and multi-output fan-out.
- Verify console ANSI behavior before touching formatters.

**Gate:** stable tests, explicit ownership behavior, no new APIs unless required.

## Phase 3 — release and measurement (later)

**Order:** `REL-01` then `DOC-01`; `PERF-01` and `CI-01` remain optional.

- Reconcile actual module tags and README instructions. **Root tag v0.2.1 does not imply adapter tag adapters/goconfig/v0.2.1.** Avoid tagging any module without an explicit release request.
- Record a baseline benchmark only when performance becomes relevant. Do not add async buffering or distributed exporters without product requirements.

## Verification reference

```sh
# Root module
make verify
go build ./examples/...

# Adapter module
cd adapters/goconfig
go mod tidy
git diff --exit-code -- go.mod go.sum
go vet ./...
go test -race ./...
go build ./examples/...
```

The GitHub CI workflow performs both modules' vet, race tests, example builds and tidy verification. An observed successful **remote CI run** does not imply a fresh local test.
