## OBS-01 — multiple OnReplace handlers on one path

**Sources:**

- [fluxlog adapter: `BindLevel`](https://github.com/majiddarvishan/fluxlog/blob/3323e1316764477b2bb1644aa397cef2fe00d575/adapters/goconfig/adapter.go)
- [goconfig v1.6.0: `Manager.OnReplace` and `findModifiableLocked`](https://github.com/majiddarvishan/goconfig/blob/v1.6.0/manager.go)

`BindLevel` registers one closure per logger with `manager.OnReplace(levelNode, handler)`. `OnReplace` **appends** a `modifiable`. `findModifiableLocked(Replaceable, path)` loops in registration order and **returns the first match**. `replaceLocked` runs only that chosen `mod.Handler`.

**Expected consequence:** If two `fluxlog.Logger` values are bound to the same manager/node/path and that path is replaced, the first logger updates; the second may retain its previous level. The manager still retains the second registration. No supported unsubscribe/deregister method was found in the inspected `Manager` API at v1.6.0; a closed Logger may remain referenced by the manager until the manager itself is released.

**Required test:** Construct a manager with `{"level":"info"}`; create two fluxlog instances with independent sinks, call `BindLevel` on both using the same level node, invoke `Manager.Replace("/level", "debug")`, and assert the observed levels of both. Record the intended supported contract **before** modifying either module.

**Decision needed:** Is one logger binding per level node the product policy, or must multiple listeners be supported? If multiple listeners are required, first evaluate a narrowly scoped upstream `goconfig` notification/registration fix rather than layering duplicate callbacks in fluxlog.

## OBS-02 — external side effect is not compensated after persistence failure

**Sources:**

- [goconfig v1.6.0: `Manager.replaceLocked`](https://github.com/majiddarvishan/goconfig/blob/v1.6.0/manager.go)
- [goconfig v1.6.0: `FileSource.setConfig`](https://github.com/majiddarvishan/goconfig/blob/v1.6.0/file_source.go)
- [fluxlog adapter: `applyLevel`](https://github.com/majiddarvishan/fluxlog/blob/3323e1316764477b2bb1644aa397cef2fe00d575/adapters/goconfig/adapter.go)

Observed sequence: `replaceLocked` sets the in-memory node to the new value, calls the registered handler (which immediately invokes `logger.SetLevelString`), and only then calls `m.source.setConfig(...)`. When that persistence operation returns an error, goconfig restores `*mod.Node = oldNode` but **does not call the original handler to undo its external side effect**. The `FileSource` can fail writing a temporary file or renaming it, so this is a reachable error path, not merely hypothetical unreachable code.

**Expected consequence:** `Manager.Replace` returns an error and the Node reverts to `info`, while the bound fluxlog Logger can remain at `debug`. This is a cross-library transaction/side-effect consistency concern; it is not proof that ordinary successful updates fail.

**Required test:** Use a real `FileSource` in a temporary directory and provoke a deterministic **post-handler** file persistence failure (without root privileges or unreliable chmod assumptions). Assert the returned error, restored node, unchanged persisted file, and actual `Logger.Level()`. Acknowledge filesystem and OS differences.

**Decision needed:** Define whether configuration persistence failures must roll back external handler effects. Avoid choosing a fix (callback compensation, delayed side effects, or a transaction protocol) until the contract and failure-injection test are agreed.

**Related note:** A rejected invalid level causes `applyLevel` to return an error **without changing the Logger**, so the simple invalid-value rollback path is different from post-handler persistence failure.

## OBS-03 — numeric timestamps with custom ConsoleWriter

**Sources:**

- [fluxlog: `timestampFormatter`](https://github.com/majiddarvishan/fluxlog/blob/3323e1316764477b2bb1644aa397cef2fe00d575/console.go)
- [zerolog v1.35.1: default console timestamp formatter](https://github.com/rs/zerolog/blob/v1.35.1/console.go)
- [zerolog v1.35.1: Unix-time encoder](https://github.com/rs/zerolog/blob/v1.35.1/internal/json/time.go)

Zerolog supports integer timestamp encodings (`TimeFormatUnix`, `TimeFormatUnixMs`, `TimeFormatUnixMicro`, `TimeFormatUnixNano`). Its own `consoleDefaultFormatTimestamp` handles `json.Number`. Fluxlog replaces that formatter with `timestampFormatter`, whose `value.(string)` check returns `""` for numeric input.

**Test:** In a non-parallel test, save/restore `zerolog.TimeFieldFormat`; test console timestamps with each Unix format and RFC3339, with `Timestamp:true`. Compare outputs while checking JSON event identity. Do not change process-global formats in parallel tests.

**Decision needed:** Confirm whether compatibility with zerolog's Unix timestamp formats is promised. If yes, add `json.Number` handling consistent with zerolog's conversion semantics while preserving existing console/JSON output.

## OBS-04 — zerolog global level still applies

**Sources:**

- [zerolog v1.35.1: `Logger.should`](https://github.com/rs/zerolog/blob/v1.35.1/log.go)
- [fluxlog: `levelWriter`](https://github.com/majiddarvishan/fluxlog/blob/3323e1316764477b2bb1644aa397cef2fe00d575/writer.go)

`zerolog.Logger.should` tests `lvl < GlobalLevel()`; this occurs before reaching fluxlog's writer. Fluxlog never mutates that process-global setting, but external code can. `SetLevel(DebugLevel)` cannot unfilter an event already suppressed by global zerolog.

**Test/policy:** Preserve/restore the zerolog global level in a serial test, set global to Error, set a fluxlog instance to Debug, emit Debug and Error, and document the effective threshold. Either narrow the guarantee in README or define new behavior explicitly; do not introduce an implicit global mutation.

## OBS-05 — NO_COLOR is not yet a defect

Zerolog's internal `colorize` function checks `NO_COLOR`, and fluxlog separately checks `NO_COLOR` for its cyan service part. A prior concern that `AlwaysColor` necessarily overrides `NO_COLOR` was **not supported by the upstream zerolog source**. Keep `FMT-02` as a routine regression test, not a bug fix.
